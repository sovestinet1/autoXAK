База проверки: `kodeandr/autoXAK`, `main`, коммит
`1198a992e55509ad241f0e15f474a76915b95458`. Проверены действующий экран

## Исправленные ошибки

При нормализации GPS относительно начала сессии появлялась ошибка двоичной
арифметики. Если первая точка получена через 2,001 секунды после старта,
отрезок ровно 30 секунд мог превратиться в `29.999999999999996` секунд.
Последующее округление вниз оставляло 29 секунд и 290 метров вместо
30 секунд и 300 метров при скорости 10 м/с. Пятисекундный отрезок со
сдвигом 3,008 секунды мог полностью отклоняться.

Теперь из времён GPS сначала вычитается время первой точки и только затем
результат переводится в секунды. Длительность всей сессии и доля покрытия
по-прежнему определяются настоящими началом и концом поездки. Пропущенное
время не дополняется прогнозом. Веса, порядок признаков и физические
константы сохранены; повторное обучение для этого исправления не требуется.

Восстановлены отдельные тесты модели и добавлены регрессии на оба случая.
Также в `app/main.py` добавлен отсутствовавший импорт `sqlalchemy.text`:
без него уже добавленная автором команда создания поля контрольного расхода
БК не выполнялась на существующей базе, а `NameError` скрывался обработчиком
исключений. Изменение `main.py` ограничено этим импортом; обработчики и
формулы не переписывались. Само обновление существующей PostgreSQL этим
локальным аудитом не проверено.

Запуск, не требующий запуска приложения и подключения к его PostgreSQL:

```sh
python -m unittest discover -s tests -p test_fuel_prediction.py -v
python -m unittest discover -s tests -p test_recording_model.py -v
```

Результат проверки: 19 тестов расчёта и 3 теста API прошли. Последние
используют отдельный FastAPI и SQLite в памяти: проверяют реальный CatBoost,
снимок автомобиля, повторное завершение, неполный профиль и сбой модели,
сохранение исходных точек и неизменность прежних финансовых счётчиков.
Они не подтверждают работу всей установленной системы с PostgreSQL,
Redis и внешними API.

## Подключение к текущему приложению: требуется отдельная доработка

1. `static/index.html` отправляет поездку в `/api/v1/telemetry/session`.
   Этот обработчик вызывает прежние `WearEngine` и `TwinEngine`, но не
   `predict_fuel`. ML вызывается только при завершении записи через
   `/api/v2/trips/{trip_id}/complete`; действующий экран этот API не использует.
2. В потоке v1 последняя скорость GPS повторяется на событиях акселерометра.
   Время исходного GPS-измерения, его точность и источник скорости теряются.
   При недостатке событий экран дополнительно создаёт искусственный поток.
   Передавать его модели как настоящую запись GPS нельзя.
3. Модель требует явные массу, объём двигателя, топливо и наличие турбины.
   При ручном сохранении автомобиля масса и объём теряются в
   `persistVehicleSelection`. Старые профили не содержат топлива и турбины,
   а `resolve_car_profile_async` подставляет параметры по умолчанию.
   Использовать такие подстановки в ML нельзя.
4. Числа «экономии» на текущем экране и в старом обработчике получены
   прежними формулами. Они не являются результатом модели расхода бензина.
   Модуль ML сейчас не моделирует альтернативную поездку и не рассчитывает
   экономию относительно цифрового двойника.
5. Расход по бортовому компьютеру в старой поездке хранится отдельно от
   записи v2. Одного значения л/100 км недостаточно для контрольных литров:
   нужны контрольный пробег и подтверждение совпадения интервала. Если
   модель обработала только часть поездки, её сумму нельзя напрямую
   сравнивать с расходом БК за всю поездку.

Для подключения следует добавить независимые исходные GPS-точки и снимок
параметров автомобиля, отдельный результат `fuel_estimate` с версией модели
и покрытием, сохранение этих данных в офлайн-очереди. При неполных данных
результат должен оставаться недоступным с понятной причиной. Прежние
результаты и функции приложения можно сохранить. Этот этап затрагивает
интерфейс и требует согласования объёма изменений.

## Что подтверждено, а что пока требует эксперимента

- Контрольные суммы обоих файлов CatBoost, карточки модели и кода признаков
  совпадают с `provenance.json`.
- Модель оценивает литры только за пригодные GPS-отрезки. Отсутствие GPS
  не считается остановкой; расход на остановках с исправной записью может
  быть положительным при принятом предположении работающего двигателя.
- Целевые значения обучения получены из MAF-телеметрии VED. Это не
  измерения расхода по топливному баку.
- Масса обучения — укрупнённая категория `Generalized_Weight` VED,
  переведённая из фунтов в килограммы. Она не равна точной снаряжённой
  массе модификации. Это ограничение переноса уточнено в `FUEL_MODEL.md`.
- Точность на GPS смартфонов и трёх пилотных автомобилях не подтверждена.
  Акселерометр, гироскоп, 2ГИС, уклон и климат текущие веса не используют.
- Для цифрового двойника потребуется отдельно построить допустимую
  альтернативную траекторию на том же маршруте и оценивать обе поездки
  одной моделью. Разница между физикой, CatBoost и гибридом не является
  экономией и не заменяет такой эксперимент.
